g1d_ws 工作原理详解

适用代码：D:\code\unitree_ws\g1d_ws（提交 068e6dd）。本文基于源代码逐模块整理，所有数值默认取自 config/g1d_nav.yaml 和代码中的缺省值。

1. 项目概述

g1d_ws 让宇树 G1-D 轮式人形机器人只用头部的 Livox Mid-360S 激光雷达和底盘轮速，在不安装 ROS 的前提下实现：高精度激光里程计、看得见悬空障碍的三维避障导航，以及一个独立于导航算法的底盘安全守护层。系统最终只向底盘写一个话题：rt/cmd_vel_no_limit（线速度 linear.x、角速度 angular.z）。

要解决的问题

原有方式的不足
  • NavGPT 给出相对航点后，底盘"先转到目标角度、再直行"，没有定位闭环，走多远靠开环时间估计。
  • 没有避障：底盘自带单线雷达只扫约 0.1 m 高的一个平面，看不到桌沿、货架隔板等悬空障碍。
  • 多个程序都可能直接写底盘速度，没有统一的限速、看门狗和急停。
本项目的方案
  • 定位：FAST-LIO2（去 ROS / PCL / Boost 改造）+ 底盘轮速外推，按升降、腰部关节实时计算雷达位姿。
  • 避障：Nav2 Costmap2D + 自研体素层（三维射线清除，保留悬空物）+ 底盘雷达层 + 膨胀；NavFn 全局规划 + Nav2 MPPI 局部控制。
  • 安全：g1d_base_guard 是底盘指令的唯一写入者，负责限幅、看门狗、扫掠路径反射停车、急停、遥控接管。
  • 接入：NavGPT 继续发"相对航点 + 图像时刻"，系统自动补偿推理延迟并返回失败原因和可通行方向。
g1d_lioC++17
10 Hz · Mid-360S → FAST-LIO2 → 位姿 / 配准点云 / 健康
g1d_navC++17

g1d_webPythonJS

运行平台：机器人 PC2（Jetson Orin NX，Ubuntu 20.04，aarch64），通信只用宇树 SDK2（CycloneDDS 0.10.x）。开发机（Windows + MinGW 或 Linux）上可以编译并测试全部算法核心，DDS 程序只能在机器人上链接。

设计要点：进程边界就是故障边界。导航算法（nav）、定位算法（lio）和安全逻辑（guard）分处不同进程，任何一个崩溃都不会让底盘失控：nav 停发指令后 guard 在 0.3 s 内减速停车；guard 本身退出后底盘依靠自身的指令超时停车。

2.2 通信方式（DDS）

  • 全部进程用 ChannelFactory::Instance()->Init(domain, net_if)（C++）或 ChannelFactoryInitialize（Python）初始化宇树 SDK2 的 CycloneDDS 通道，域默认为 0，网卡为 system.net_if（eth0）。
  • 消息类型全部使用 SDK2 自带的 ROS 2 兼容 IDL：Odometry_、PointCloud2_、Twist_、String_、OccupancyGrid_、LowState_ 等。复杂结构（目标、状态、健康、调试、参数）一律用 String_ 承载 JSON，便于扩展和人工查看。
  • 唯一的例外是底盘雷达 LaserScan_：SDK2 C++ 侧没有现成类型支持，所以由 Python guard（复制了真机验证过的 slamware_idl.py 定义）订阅后转成 base_link 下的 PointCloud2_，再发布到 rt/nav/chassis_scan 给 C++ 使用。这样 C++ 不需要运行 idlc 生成代码。
  • C++ 侧的 DDS 回调线程只负责把消息塞进 bus::Mailbox（带上限的线程安全队列），主循环每个周期 drain() 一次，算法核心因此是单线程的。
  • deploy/cyclonedds.xml 固定网卡并加大接收缓冲，由环境变量 CYCLONEDDS_URI 引用。

2.3 启动与退出顺序

  1. guard 最先启动：用 DDS 发现（dds_discovery.find_writers）检查 rt/cmd_vel_no_limit 是否已有其他写入者，默认 other_writers: refuse，即拒绝启动。随后调用底盘 HTTP 中止当前动作。启动后保持静默，不发布任何指令。
  2. web 随后启动（可选）。
  3. lio 启动，机器人需静止约 2 s：FAST-LIO2 用前几帧的 IMU 数据估计重力方向和零偏（INIT_TIME），之后 ekf_inited 才为真。
  4. nav 最后启动：收到第一帧有效 LIO 后锚定 odom 原点。
  5. 退出时按相反顺序：run_all.sh 的 cleanup 倒序向各进程发 SIGINT，nav 退出前发一条零速，guard 最后退出，若仍在运动则连发 3 次零速。

3. 坐标系与位姿链

头部雷达会随升降和腰部一起运动，所以"雷达位姿"和"底盘位姿"之间不是固定外参，而是一条随关节变化的运动链。理解这条链是理解整个系统的关键。

锚定（第一帧有效 LIO，认为底盘水平地放在地面上）： T_odom_lio = T_base_imu(q₀) · T_lio_imu(t₀)⁻¹ → 使 t₀ 时刻 base_link 恰好位于 odom 原点 此后每一帧： T_odom_base(t) = T_odom_lio · T_lio_imu(t) · T_base_imu(q(t))⁻¹ → 投影为 2D 位姿 (x, y, yaw)

为什么要"姿态锁定"：如果导航中手臂、腰部或升降在动，头部 IMU 的运动就不全是底盘运动。只要运动学模型有一点误差，就会被误当成底盘位移。所以导航时要求身体保持在标定好的"导航姿态"，偏离 lock_tolerance（腰 2°、手臂 5°、升降 1 cm、升降速度 5 mm/s）立即以 body_moved 结束目标。

4. 一帧数据的完整旅程

下面按时间顺序，跟踪一帧雷达数据从传感器到底盘电机的全过程。这是理解各模块如何配合的最快方式。

  1. 雷达出点（g1d_lio，Livox 线程）：Livox-SDK2 回调收到 Cartesian High 点包（每包若干点 + 起始时间戳 + 点间隔）和 IMU 包（200 Hz，加速度单位 g）。IMU 立即推入 FAST-LIO 缓冲，同时喂给 ClockMapper 估计"主机时间 − 雷达时间"。
  2. 拼帧：FrameAggregator 按 100 ms 把点包拼成一帧，给每个点算出相对帧起点的时间偏移（毫秒），用于运动去畸变。
  3. 预处理：去掉非正常回波（tag）、重复点、0.6 m 以内（打到自己）和 60 m 以外的点，再删掉落在"自身点过滤框"（头、躯干、立柱、收拢的手臂）内的点。
  4. FAST-LIO2（g1d_lio 主线程）：IMU 前向积分 + 反向去畸变 → 降采样 → 在 ikd-Tree 地图里找最近 5 点拟合平面 → 迭代误差状态卡尔曼滤波更新位姿 → 把新点加入地图。仿真中单帧约 7 ms。
  5. 发布：rt/nav/lio_odom（IMU 在 odom_lio 的位姿）、rt/nav/registered_cloud（去畸变后的当前帧，世界系，5 cm 降采样）、rt/nav/lio_health（JSON），三者使用同一个主机时间戳。
  6. 配对（g1d_nav 主循环）：把点云和同一时间戳（误差 < 1 ms）的 LIO 位姿配成 LioInput，并检查健康消息是否 ok 且时间接近。
  7. 状态估计：用当前关节算 T_base_imu，得到底盘 2D 位姿；与轮速里程计做一致性检查；在两帧 LIO 之间用轮速增量外推。
  8. 更新地图：点云变换到 odom，送入局部（6×6 m）和全局（20×20 m）代价地图的体素层：先三维射线清除，再标记障碍。同时生成 base_link 下的 3 m 内障碍点，发布给 guard 做反射层。
  9. 控制周期（20 Hz）：滚动地图原点 → 合成代价并膨胀 → 状态机检查安全条件 → 必要时 NavFn 重规划（每 1 s 或路径被堵）→ MPPI 采样 1000 条轨迹求最优速度 → 发布 rt/nav/cmd_vel。
  10. guard（30 Hz）：取最新的 nav 指令 → 限幅 → 检查底盘雷达和障碍点是否新鲜 → 整车矩形沿指令圆弧扫掠求净距 → 减速 / 停车 → 加速度限制 → 写入 rt/cmd_vel_no_limit。
延迟预算：雷达帧 100 ms（帧内去畸变）+ LIO 处理约 10 ms + nav 周期 50 ms + guard 周期 33 ms。nav 用轮速把 LIO 位姿外推到"当前时刻"（最多 0.3 s），所以控制用的位姿延迟远小于 100 ms。障碍点只有在新 LIO 帧到达时才更新（10 Hz），guard 认为超过 0.5 s 未更新即"过期"。

5.2 帧聚合与逐点时间（FrameAggregator）

Livox 雷达是非重复扫描，数据以小包连续到达，不存在天然的"一圈"。FAST-LIO 需要一帧点云及每个点的采集时刻，以便用 IMU 轨迹把每个点校正到帧末时刻（运动去畸变）。

点间隔(ns) = packet.time_interval × 100 / 点数 （time_interval 单位为 0.1 µs） 第 i 个点时间 t_i = packet.timestamp_ns + i × 点间隔 t_i ≥ 帧起点 + 100 ms → 输出当前帧；下一帧起点 = 上一帧起点 + 100 ms（帧首尾相接，不留缝） 点的 offset_ms = (t_i − 帧起点) / 1e6 → 存入 PCL 点的 curvature 字段（沿用 FAST-LIO 约定）

若时间戳倒退超过一帧（雷达重启或时钟跳变），丢弃未完成的半帧并重新开始。

5.3 预处理与自身点过滤（preprocessFrame）

  1. 回波标签：只保留 Livox tag 第 4–5 位为 0x00 或 0x10 的正常回波（与 FAST-LIO 原版判断相同），过滤雨雾、拖尾等噪点。
  2. 抽稀：每 point_filter_num（默认 1，即不抽稀）个有效点取一个。
  3. 去重：与前一点坐标完全相同的点丢弃。
  4. 距离：r ≤ blind（0.6 m）或 r > max_range（60 m）的点丢弃。
  5. 自身点过滤：SelfFilter 用 head_to_livox 把点变换到 head_link，若落在任一 self_filter.boxes 盒子 [xmin,xmax,ymin,ymax,zmin,zmax] 内则删除。默认两个盒子：头 + 躯干 + 立柱，以及收拢的手臂。这样机器人自己既不会成为 LIO 的"特征"，也不会成为代价地图里的"障碍"。

5.4 FAST-LIO2 内部流程（fast_lio_api::process）

FAST-LIO2 的算法代码（IESKF、ikd-Tree、IMU 处理）保持上游 7cc4175 原样，只把 ROS 节点 laserMapping.cpp 改造成可嵌入的 5 个函数：init / push_imu / push_scan / process / reset。上游使用全局变量，因此每个进程只能有一个 LioEstimator（构造函数里用原子计数强制检查）。

  1. 同步（sync_packages）：取最早一帧点云，帧末时刻 = 帧起点 + 最后一个点的偏移；等到 IMU 缓冲覆盖到帧末才处理，并取出这段时间内的全部 IMU。
  2. IMU 处理（ImuProcess::Process）：启动阶段用静止 IMU 均值初始化重力方向、陀螺零偏；之后对每个 IMU 采样做前向传播（状态与协方差），再按逐点时间反向传播，把帧内每个点补偿到帧末时刻的 IMU 位姿（去畸变）。
  3. 地图视野裁剪（lasermap_fov_segment）：机器人移动到局部地图边界附近时，删除 cube_side_length（1000 m）立方体以外的地图点。
  4. 降采样：当前帧按 filter_size_surf（0.3 m）体素降采样。第一帧直接建立 ikd-Tree。
  5. 迭代误差状态卡尔曼滤波（update_iterated_dyn_share_modified）：每次迭代对每个点（OpenMP 并行）在 ikd-Tree 中找 5 个最近邻，最远邻平方距离 ≤ 5 m² 时用最小二乘拟合平面（esti_plane，阈值 0.1 m），点到平面距离作为观测残差，筛掉 1 − 0.9·|d|/√‖p‖ ≤ 0.9 的点；以流形上的 IESKF 求解 23 维状态（位置、姿态、速度、陀螺 / 加速度零偏、重力、雷达-IMU 外参），最多迭代 max_iteration（3）次。
  6. 地图增量更新（map_incremental）：把降采样后的点变换到世界系，按 filter_size_map（0.4 m）体素判断是否需要加入，增量插入 ikd-Tree，地图无需重建。
  7. 输出（本项目新增）：帧末时刻、IMU 位姿 / 速度 / 零偏 / 重力、6×6 位姿协方差、输入 / 降采样 / 有效点数、平均残差、法向量矩阵最小特征值，以及去畸变后的整帧世界系点云。

LioEstimator::process() 再把帧末雷达时间映射成主机时间、算出雷达原点在世界系的位置（供射线清除用）、把点云按 publish_cloud_voxel（5 cm）降采样，并更新健康状态。

5.5 健康监测与退化检测（LioHealth）

z_drift高度相对首帧漂移 > 0.3 m（轮式底盘在平地上不应有高度变化）累计漂移、外参错误
degenerate（标志）所有匹配平面法向量 n 的 mean(n·nᵀ) 最小特征值 < 0.02长走廊、单面墙：某个方向没有几何约束

单帧异常可以容忍；连续 bad_frames_to_fail（3）帧异常，或 EKF 尚未初始化，或出现 NaN，则 ok=false。g1d_nav 在 require_lio: true 时会以 lio_lost 终止导航。

退化检测的直观含义：若所有匹配到的平面法向量都近似垂直于走廊方向，那么 Σ n nᵀ 在走廊方向上的分量接近 0，滤波在这个方向上缺少约束，位置会"滑动"。最小特征值就是这种约束强度的度量。

5.6 时钟映射（ClockMapper）

Mid-360S 的时间戳通常是雷达上电后的时间，与主机时钟无关。而 NavGPT 的延迟补偿、点云与位姿配对都需要统一的主机时间。做法：

每个 IMU 包：offset_k = host_recv_time − sensor_stamp （传输排队只会让它变大） offset = 最近 10 s 内 offset_k 的最小值 （单调队列 O(1) 维护） host_time(sensor_t) = sensor_t + offset 若 offset 的变化超过 50 ms → jumps += 1（时钟重置或漂移，在 lio_health 中报告）

最小值剔除了网络和调度带来的正向抖动，得到"零排队延迟"下的偏移估计。lio_health 中的 clock_offset 应保持稳定，clock_jumps 应为 0。

6.3 状态估计（StateEstimator）

目标：在 10 Hz、带延迟的 LIO 和约 20 Hz 的轮速之间，给 20 Hz 控制提供连续、低延迟、无跳变的 base_link 位姿。

(1) 收到 LIO 帧

  • 若尚未锚定，计算 T_odom_lio（见第 3 节）。
  • 计算 T_odom_base，投影成 Pose2D，保存为"LIO 锚点"（时间戳 + 位姿），写入 10 s 的 LIO 历史；用相邻两帧之差计算 LIO 速度。
  • 一致性检查：比较过去 consistency_window_s（2 s）内 LIO 的位姿增量和轮速里程计的增量。平移差 > 0.3 m 或偏航差 > 10° → odom_consistent=false（打滑、被推动、LIO 漂移时会出现）。该标志目前只在状态中报告，不终止导航。

(2) 每个控制周期 estimate(now)

lio_ok = LIO 健康 且 now − 锚点时间 ≤ lio_timeout_s (0.5 s) wheel_ok = now − 最近轮速时间 ≤ wheel_timeout_s (0.3 s) 若 lio_ok： pose = 锚点位姿 若 wheel_ok：pose = pose ⊕ (轮速位姿(锚点时刻)⁻¹ ⊕ 最新轮速位姿) ← 轮速增量叠加到 LIO 锚点 速度 = 轮速速度，source = "lio+wheel" 否则： 速度 = LIO 差分速度，source = "lio" dt = clamp(now − 最近数据时刻, 0, max_extrapolation_s = 0.3) pose = pose ⊕ (v·dt, 0, w·dt) ← 匀速外推到当前 valid = true 否则若 allow_wheel_only（默认 false）：用轮速从最后一个 LIO 锚点推算，source = "wheel" 否则 valid = false ← 定位丢失

每个周期的估计值写入 10 s 的位姿历史 history_，供 poseAt(stamp) 查询任意过去时刻的位姿（线性插值）。这正是 NavGPT 延迟补偿的基础（第 8 节）。

为什么轮速只用"增量"：轮速里程计长期会漂移，但短时间增量很准、延迟低；LIO 长期准确但有 100 ms 帧延迟。每来一帧 LIO 就重新锚定，轮速只负责填补两帧之间的空白，两者的优点都保留了，也不会累积轮速误差。

6.4 代价地图

两张地图都以机器人为中心滚动，结构相同（LayeredCostmap），参数不同：

地图尺寸 / 分辨率体素层范围更新用途
local6 × 6 m，0.05 m（120×120）标记 5 m，射线 6 m，每点清除每个控制周期MPPI 的 CostCritic、路径堵塞检查、旋转 / 直线段安全检查、可通行扇区
global20 × 20 m，0.1 m（200×200）标记 8 m，射线 9 m，每 2 点清除一次开始目标和重规划前（间隔 ≥ 0.2 s）NavFn 全局规划、目标合法性检查

每次 update(robot_pose) 的步骤

  1. 滚动：主栅格和各图层原点移到 robot − size/2，按整格平移，重叠区保留，新进入的格子置为初值（RollingGrid::updateOrigin，语义与 Nav2 Costmap2D::updateOrigin 相同）。
  2. 衰减：decay_s > 0 时清除过旧的体素列。默认 decay_s: 0，障碍一直保留，直到被射线清除。这样障碍进入雷达 0.6 m 近距离盲区后仍然存在。
  3. 清除车体：机器人轮廓内的体素和雷达格清零（机器人占据的空间不可能是障碍）。
  4. 合成：主栅格重置为 FREE(0)，体素层与底盘雷达层的占据格写入 LETHAL(254)。
  5. 膨胀：InflationLayer 只从障碍边界格出发，用预计算的圆形核叠加代价（取最大值）。

VoxelLayer：为什么能看见悬空障碍

每个 2D 栅格存一个 uint32 位掩码，表示这一列在各高度层是否有障碍：z_min 0.08 m 到 z_max 1.85 m、每层 0.1 m，共 18 层。另有命中计数和时间戳。

  • 标记：点在 [0.08, 1.85) 高度带内且距离 ≤ 5 m 时，置位对应列的对应层。地面点（z < 0.08）不会被标记，机器人头顶以上（≥ 1.85 m）也不考虑。
  • 清除：从雷达原点到每个点（最远 6 m）做 Amanatides–Woo 三维体素遍历，只清除射线真正穿过的（列, 层）位，终点格保留。
  • 先清后标：同一帧先做全部射线清除再标记，所以本帧的点不会被本帧的射线擦掉。
  • 列中任一位为 1（且命中数 ≥ min_points_per_column）就写成 LETHAL。

ScanLayer：底盘单线雷达

沿每束激光以半格步长做二维清除（终点格除外），终点在 4 m 内则标记为障碍。inf 或超量程的读数默认视为无效（inf_is_valid: false），不做清除。它补上了头部雷达看不到的近地低矮障碍（头部雷达 0.6 m 盲区内、或被车身遮挡的区域）。

InflationLayer：膨胀

与 Nav2 InflationLayer::computeCost 完全相同的公式。内切半径由轮廓 [±0.30, ±0.28] 计算得 0.28 m：

d = 0 → 254 LETHAL（障碍本身） d ≤ r_inscribed(0.28) → 253 INSCRIBED（机器人中心在此必然碰撞） d ≤ radius(0.55) → cost = 252 · exp(−cost_scaling_factor(3.0) · (d − 0.28)) d > 0.55 → 0 FREE

InflationLayer 同时实现了 MPPI 需要的 InflationLayerInterface（提供 cost_scaling_factor 和内切半径），所以 Nav2 MPPI 的 CostCritic 可以直接使用。发布为 OccupancyGrid_ 时采用与 Nav2 Costmap2DPublisher 相同的映射：255→−1，254→100，253→99，其余线性映射到 1–98。

6.5 NavFn 全局规划（GlobalPlanner）

目标合法性检查 sanitizeGoal（开始目标时执行一次）

  1. 距离 > max_goal_distance（9 m）→ 沿直线截断到 9 m，partial=true（全局地图半宽只有 10 m）。
  2. 目标在全局地图外 → goal_out_of_range。
  3. 目标格代价 ≤ goal_max_cost（128）或未知 → 合法。
  4. 否则沿"目标 → 机器人"方向逐格回退，找到第一个可接受的格子 → adjusted=true。
  5. 仍找不到 → 在 goal_search_radius（0.5 m）内按圆环由近到远搜索。
  6. 都失败 → goal_in_obstacle。

路径规划 makePlan（流程与 Nav2 NavfnPlanner 一致）

  1. 复制全局代价栅格，把机器人所在格设为 FREE（机器人所在处不可能是障碍）；allow_unknown: true 时未知格可通行。
  2. NavFn 以机器人位置为源做 Dijkstra（或 A*）波前扩散，计算整张图的"导航势场"，每格的势 = 从机器人出发的累计代价（格子代价越高，扩散越慢）。
  3. 检查目标格的势；若不可达，在 tolerance（0.3 m）方框内找最近的可达格。
  4. 从目标出发沿势场梯度下降回到机器人，得到路径后反转（最多 4 × max(nx, ny) 步）。
  5. 按 path_spacing（5 cm）重采样，每点朝向取指向下一点的方向；末点朝向在 use_yaw 时取目标朝向。

导航中每 1/replan_hz（1 s）重规划一次；若 MPPI 当前跟踪的局部路径上任一点在局部地图中代价 ≥ 253（被新出现的障碍挡住），立即重规划。

6.6 MPPI 局部控制（MppiController）

直接使用 Nav2 nav2_mppi_controller 的 Optimizer（Eigen 实现）。ros_shim 提供一个进程内的 nav2::LifecycleNode，g1d_nav.yaml 的 mppi: 段被原样加载为 FollowPath.* 参数，参数名与 Nav2 完全一致。

MPPI（模型预测路径积分）每个周期做的事

  1. 路径裁剪（复刻 Nav2 controller_server）：在上次最近点之后 search_window（2 m）内找离机器人最近的路径点，从那里截取 prune_distance（1.7 m）且位于局部地图内的路径段作为参考。
  2. 采样：以上一周期的最优控制序列（56 步 × [vx, wz]）为均值，加上高斯噪声（vx_std 0.2、wz_std 0.4），生成 1000 条候选控制序列。
  3. 约束：裁剪到 vx ∈ [−0.10, 0.40]、|wz| ≤ 0.60，并满足加速度限制 ax ∈ [−1.0, 0.5]、|az| ≤ 1.0；本目标的限速通过 setSpeedLimit 生效。
  4. 推演：用差速模型（DiffDrive）积分 56 × 0.05 s = 2.8 s 的轨迹：x += v·cosθ·dt, y += v·sinθ·dt, θ += w·dt。
  5. 评价：每条轨迹由 8 个评价项打分求和，得到代价 Sk。
  6. 加权平均：wk = exp(−(Sk − min S) / temperature)（temperature = 0.3，gamma 0.015 为控制代价项），新的最优序列 = Σ wk·uk / Σ wk。
  7. 执行：输出序列第一步作为本周期速度，序列整体前移一步，作为下一周期的初值（热启动）。全部轨迹都碰撞时抛出 NoValidControl，NavCore 会在 1 s 后进入恢复。

6.7 目标状态机（NavCore）

开始一个目标（startGoal）

  1. 前置检查：定位无效 → lio_lost；急停中 → guard_estop；不在导航姿态 → body_not_locked。
  2. 确定参考位姿：frame="base_at_stamp" 时用 poseAt(stamp) 查历史位姿；查不到且 stamp 超过 5 s 或在未来 1 s 以后 → goal_stamp_unavailable；否则用当前位姿。
  3. rotate 模式：目标朝向 = 参考朝向 + yaw（或 odom 绝对朝向），进入 ROTATING。
  4. 其余模式：目标 = 参考位姿 ⊕ (x, y, yaw)；未指定 yaw 时，朝向取"机器人 → 目标"方向（不做末端对齐）。
  5. 更新全局地图 → sanitizeGoal → navigate 模式规划路径并交给 MPPI，设置限速 → 进入 NAVIGATING。

NAVIGATING 每个周期（stepNavigate）

  1. 末端对齐：位置进入 xy_tolerance（0.2 m）后，若需要对齐且朝向误差 > 0.25 rad，进入原地旋转（P 控制 w = clamp(1.5·err, ±0.5)，最小 0.15 rad/s）；旋转前检查轮廓在 0.3 rad 范围内是否会碰撞，被挡超过 3 s 就以 SUCCEEDED + yaw_not_reached 结束。
  2. 进度检查：8 s 内到目标的距离没有减少"所需进度"就进入恢复。所需进度 = clamp(0.5·(dist − tol), 0.02, 0.2)，即越接近目标要求越小（距目标 0.25 m 时不可能再前进 0.2 m）。
  3. simple 模式：转向目标（误差 > 0.15 rad 时原地转），再直行 v = min(0.3, 0.6·d + 0.05)，前方 1.5 m 内按 0.1 m 步长做轮廓碰撞检查，被挡直接 blocked 失败。这是保留的"旧方式"闭环版本，用于对照。
  4. 末段直线接近：距目标 < approach_distance（0.6 m），且机器人到目标的直线段整车无碰撞时，绕过 MPPI，用简单 P 控制直线接近：v = min(0.2, 0.8·d + 0.03)。这样可以避免 MPPI 在目标附近徘徊、停滞。
  5. 重规划：到期（1 s）或局部路径被堵时，更新全局地图并重规划；失败则进入恢复（no_path）。
  6. MPPI：计算速度；连续失败超过 mppi_fail_tolerance_s（1 s）进入恢复（blocked）。

恢复行为（RECOVERING）

按 manager.recovery 顺序执行，每个目标每种动作只用一次，全部用完则 FAILED（原因 blocked 或 no_path）：

动作做什么目的
wait停车等待 2 s等动态障碍（行人）离开，期间射线会把离开的人清除
clear清除局部和全局地图中距机器人 1.5 m 以外的障碍清掉过时或幽灵障碍（decay_s=0 时障碍不会自己消失）
rotate向可通行扇区更多的一侧原地转 0.52 rad（30°），最长 5 s，转动不安全时提前结束刷新视野，让雷达看清侧方

每个动作完成后回到 NAVIGATING，重置进度计时，强制立即重规划并重置 MPPI。

可通行扇区（free_sectors）

在 −90°、−60°、…、+90° 共 7 个方向上，从 0.3 m 到 1.5 m 每 0.15 m 放一次整车轮廓（朝向为该方向），只要有一处轮廓代价达到 LETHAL，该方向就不可通行。结果随状态发布，供恢复动作选择旋转方向，也供 NavGPT 在失败后重新决策（"可通行方向 = −30,0,30"）。

6.8 输出与障碍点

onLio() 中除了更新地图，还为 guard 生成 rt/nav/obstacle_points：把本帧 odom 系点云变换到当前 base_link，保留满足下列条件的点，并按 5 cm 体素去重：

  • 高度在体素层高度带 [0.08, 1.85) 内（因为 odom 的 z=0 就是地面，直接用 odom 的 z 判断）；
  • 水平距离 ≤ guard.obstacle_points_range（3 m）；
  • 不在车身轮廓内。

这样 guard 不需要知道任何坐标变换和运动学，直接拿到"车体坐标系下、与车身同高度范围内的三维障碍点"（投影到 xy 使用），桌沿这类悬空障碍也包含在内。

7. g1d_base_guard：安全守护

源码：python/g1d_nav_py/guard_core.py（纯逻辑、可单测，不依赖 DDS）和 guard_node.py（DDS / HTTP 适配）。逻辑与通信分离，所以 14 项 guard 单元测试可以注入时钟，精确验证每条规则。

7.1 30 Hz 处理流水线（GuardCore.step）

  1. 选择指令源（优先级从高到低）：
    • 急停锁存中，或遥控器接管期内 → 目标 (0, 0)；
    • Web 遥控 rt/nav/teleop_cmd 在 0.3 s 内 → 用遥控指令，先限制在 teleop_vx_max 0.30 / teleop_wz_max 0.50（deadman：浏览器停发 0.3 s 即停）；
    • 导航 rt/nav/cmd_vel 在 cmd_timeout（0.3 s）内 → 用导航指令；
    • 否则 → (0, 0)（看门狗）。
  2. 限幅：vx ∈ [−0.10, 0.50]，|wz| ≤ 0.60。
  3. 传感器新鲜度：底盘雷达超过 0.5 s 未更新 → scan_stale；require_cloud: true 时 Mid-360S 障碍点超过 0.5 s 未更新 → cloud_stale。两种情况都只允许停车。障碍点集合 = 底盘雷达点 ∪ Mid-360S 障碍点，去掉车身框 |x|<0.30, |y|<0.28 内的点。
  4. 前进反射（vx > 0）：沿指令圆弧扫掠，求净距 d（7.2 节）。d < stop_m（0.45 m）→ 停车，并且禁止原地转（front）；d < slow_m（1.2 m）→ 线性减速：
    v = max( v · (d − 0.45) / (1.20 − 0.45), min(v, creep_v = 0.05) )
    爬行速度下限保证车能真正开到停车线，而不是无限趋近。
  5. 后退反射（vx < 0）：同样扫掠，后方 rear_clear_m（0.5 m）内有障碍 → 禁止后退（rear）。
  6. 旋转保护：|v| < 0.05 且 w ≠ 0 时，若半径 rotate_radius（0.38 m）圆内、车身框外有障碍点 → 禁止旋转（rotate）。
  7. 加速度限制：加速 acc_v 0.5 m/s²，减速或换向 brake_v 1.5 m/s²，角加速度 acc_w 1.0 rad/s²。急停或遥控接管时不做斜坡，直接置零。
  8. 是否发布（7.3 节）。

其他输入

  • 急停：rt/nav/estop "on" 锁存，"off" 人工解除。底盘 HTTP 事件 BUMPER_TRIGGERED / CLIFF_DETECTED 也会锁存急停（后台线程每 0.5 s 轮询，EventTracker 只认启动后新出现的事件）。
  • 遥控器接管：rt/wirelesscontroller 任一摇杆偏移 > 0.15 → 此后 5 s 内 guard 完全不发布，让遥控器直接控制底盘。guard_state 中 manual=true，g1d_nav 因此以 manual_override 取消目标。
  • 底盘雷达转发：LaserScan_ → scan_to_points（按安装位置 robot.chassis_laser 变换到 base_link）→ 既用于反射层，又以 PointCloud2_ 发布到 rt/nav/chassis_scan。
  • 参数热更新：rt/nav/param_set（target: "guard"）只接受白名单参数，并检查范围（如 stop_m ∈ [0.1, 2.0]，且必须满足 slow_m > stop_m），结果通过 rt/nav/param_state 回执。
  • 状态输出：10 Hz rt/nav/guard_state（拦截原因、急停、人工接管来源 remote / web、指令源、前后净距、各输入的年龄与计数），同时写入 logs/guard-*.jsonl。

7.2 扫掠路径反射层（swept_clearance）

固定扇区或直走廊的检查有两个问题：转向避让时会误停，向障碍转弯时停得太晚。guard 改为把整车矩形（前沿 0.28 m、后沿 0.30 m、半宽 0.30 m）沿当前指令 (v, w) 决定的圆弧向前"扫"，求第一次碰到障碍点时走过的弧长。

算法（向量化 numpy）：

k = w / |v| |k| < 1e-3（直行）： 命中 = |y| ≤ 半宽 且 x·sgn(v) > 前沿 d = min(x·sgn(v) − 前沿) 否则（圆弧）： 步长 ds = min(0.05 m, 0.05 rad / |k|) s_max = min(查找距离, (π/2) / |k|) ← 最多看四分之一圈 对每个 s：θ = k·s 车体中心 = (sgn·sin θ / k, sgn·(1 − cos θ) / k) 把所有障碍点变换到该处车体坐标系 命中 = −后沿 ≤ lx ≤ 前沿 且 |ly| ≤ 半宽 d = 第一次命中前一步的 s

前进时查找距离为 slow_m（1.2 m），后退为 rear_clear_m + 0.5。

7.3 发布策略与单一写入者

  • 启动时静默：t_zero 初值为 −∞，没有运动就不发布，不会抢遥控器或其他控制源。
  • 运动中以 30 Hz 持续发布；速度归零后再持续发布 zero_hold（1 s，需用 cmd_vel_probe.py 实测底盘行为后确定），然后停止发布，让底盘"松开"（有的底盘收到零速会锁轮，影响推车）。
  • 遥控器接管期间不发布。
  • 单一写入者：启动时用 DDS 发现检查 rt/cmd_vel_no_limit 的其他写入者；g1d_nav、g1d_web、NavGPT 都不直接写底盘，Web 遥控也经 guard 转发，同样受反射层约束。
  • 退出时若仍在运动，连发 3 次零速。

8. NavGPT 接入与延迟补偿

NavGPT 看一张图片，推理出一个相对航点 (dx, dy, dyaw)（base_link：x 前、y 左、逆时针为正）。问题是：推理需要时间，等结果出来时机器人可能已经移动或转动了。如果直接把航点加到"当前位姿"上，目标就错了。

  1. 相机帧在主机时间 t_recv 收到，t_img = t_recv − camera_latency_s（例如 0.08 s）。
  2. NavGPT 推理若干秒，返回 (dx, dy, dyaw)。
  3. NavGptBridge.send() 通过 NavClient 发布目标：frame="base_at_stamp"、stamp=t_img、限速 0.35 m/s、容差 0.2 m / 0.25 rad、超时 60 s。
  4. g1d_nav 用 poseAt(t_img) 从 10 s 位姿历史中取出拍照那一刻的底盘位姿 Pimg，目标 = Pimg ⊕ (dx, dy, dyaw)，再转换为 odom 绝对坐标，此后与机器人怎么动无关。
  5. NavClient.wait() 订阅 rt/nav/status，按 goal_id 等待结束状态。
  6. NavGptBridge.feedback() 生成下一轮提示词：成功返回空字符串（或 [导航完成] yaw_not_reached）；失败返回 [导航失败] 原因=blocked（已部分前进） 可通行方向(度,左正)=-30,0,30。
from g1d_nav_py.nav_client import NavClient
from g1d_nav_py.navgpt_bridge import NavGptBridge

bridge = NavGptBridge(NavClient(0, "eth0"), camera_latency_s=0.08, max_speed=0.35)
result = bridge.step(lambda: navgpt3.infer(image, instruction), t_recv=frame_recv_time)
prompt += bridge.feedback(result)   # 失败时附带原因和可通行方向
精度前提：延迟补偿依赖主机时间一致。所有跨进程时间戳都使用 CLOCK_REALTIME（nowSec() / time.time()），NavGPT 若运行在另一台机器上，需要与 PC2 做 NTP / PTP 同步。

9.1 后端结构

Hub（hub.py）
DDS 读取线程。订阅 15 个话题，只保存每个话题的最新值、接收时间、频率计（3 s 窗口）和版本号；提供 goal / estop / teleop / param_set 发布者。不接触 asyncio。
WebApp（app.py）
单个 asyncio 循环，20 Hz 轮询 Hub 的版本号，有变化才打包推送。负责控制锁、命令分发、任务运行器、验收测试、地图构建与导出。
前端（static/）
scene.js：3D / 俯视视图和 13 个图层；main.js：7 个标签页（导航、任务、遥控、建图、测试、参数、诊断）；net.js：WebSocket 通信。

9.2 推送协议

  • 文本帧（JSON）：hello（配置、轮廓、测试目录）、state（10 Hz：status / guard / lio / debug / 位姿 / 指令 / 任务 / 测试 / 地图统计 / 控制权，每 1 s 附带话题频率表）、params、event 等。
  • 二进制帧：struct "<B3xI"（1 字节类型 + 3 字节填充 + 4 字节头长度）+ JSON 头（填充到 4 字节对齐）+ float32 xyz 数组。类型：1 当前帧、2 地图增量、3 地图重置、4 障碍点、5 底盘雷达、6 局部代价地图、7 全局代价地图。
  • 两种队列：当前帧、障碍点、代价地图等用"槽位"，只保留最新一份，网络慢就丢旧数据；地图增量用有序"流"，积压超过 400 包则清空队列，下次重发完整地图（每包 20 万点）。WebSocket 缓冲超过 2 MB 时暂缓发送。

11. 免 ROS 移植的实现方式

项目的一个核心工程目标：算法与上游开源实现保持一致（便于信任与跟进），同时机器人上不装 ROS、PCL、Boost。做法是"原样 vendor + 垫片 + 少量可追溯补丁"。

手段做法
src/ros_shim最小 ROS 2 API 垫片，只实现 vendored Nav2 代码用到的符号：rclcpp 日志宏（输出到 stderr，级别由 G1D_LOG_LEVEL 控制）、参数系统（进程内键值表 nav2::LifecycleNode，由 YAML 填充）、时间、消息结构体（字段名与 ROS 一致，无序列化）、tf2 工具函数、angles、Costmap2DROS 门面。
pluginlib 静态注册PLUGINLIB_EXPORT_CLASS 在静态初始化时把工厂函数登记到注册表；MPPI 的运动模型、评价项、轨迹校验器因此可以按名字创建。相关目标文件必须整体链接（CMake WHOLE_ARCHIVE，并为 CMake 3.16 提供兼容分支）。
src/pcl_lite替代 PCL 的点类型、PointCloud 和 VoxelGrid，满足 FAST-LIO 和输出降采样的需要。
IKFoM 去 Boost只保留 Boost.Preprocessor 头文件（子模块）。
fast_lio_apilaserMapping.cpp 中的 ROS 订阅 / 发布 / tf / PCD 保存全部去掉，换成 init / push_imu / push_scan / process / reset；IESKF 和 ikd-Tree 算法未改。
核心与 DDS 分离g1d_common / g1d_lio / g1d_nav 库不依赖 SDK，在 Windows（MinGW）上也能完整编译和测试；只有 src/apps 链接 unitree_sdk2（Linux 专用）。开发机上对 SDK 头文件做 -fsyntax-only 检查，曾借此发现并修复 g1d::dds 与 CycloneDDS ::dds 的命名冲突。
LaserScan 转发见 2.2 节，C++ 侧因此只使用 SDK 自带的消息类型。
依赖管理未修改的依赖用 git 子模块（Eigen 3.4.0、yaml-cpp 0.8.0、Livox-SDK2、unitree_sdk2、unitree_sdk2_python、boost_preprocessor）；修改过的上游代码 vendor 进仓库（先原样提交、再修改），说明见 third_party/*/UPSTREAM.md；单文件库 nlohmann/json、doctest、three.js 随仓库提供。

16. 已知限制

  • 不保存地图、不做重定位：每次启动 odom 原点就是启动位置，Web 导出的地图只用于查看和记录。全局地图只有机器人周围 20 × 20 m，目标距离被截断到 9 m。
  • 动态障碍没有运动预测：行人只靠体素射线清除和 guard 反射层处理。
  • 几何退化场景：长走廊、空旷大厅中 LIO 可能失效（健康监测会报告并停止导航）；degenerate 目前只作为标志报告。
  • 假设地面水平：T_odom_lio 锚定和高度带判断都假设底盘水平放在平地上；坡道、门槛会影响高度带的准确性。
  • 导航时身体必须保持姿态：不支持边走边动手臂或升降。
  • odom_consistent 只报告不处理：LIO 与轮速不一致时目前不会自动终止导航。
  • 若干参数（外参、身体链偏移、底盘指令行为）必须在真机上实测，见 docs/DEPLOYMENT.md 和 docs/CALIBRATION.md。
